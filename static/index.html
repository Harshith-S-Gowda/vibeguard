RESEARCH SPECIFICATION

1. Problem Context & Scientific Hypothesis

Addressing the critical blindspot of AI vibe-coding in embedded & IoT systems.

FORMAL RESEARCH HYPOTHESIS
"Combining package-name similarity, publisher metadata, and hardware-aware source-code analysis can improve identification of suspicious embedded dependencies compared with name-similarity-only detection."

Vibe Coding Risk

AI-assisted development speeds up software creation, but AI-written projects frequently import third-party dependencies without inspection. In microcontrollers, libraries execute with raw memory access, unprotected hardware peripherals, and unsegmented WiFi credentials.

Embedded Context

ESP32 and Arduino projects import sensor, communication, and utility libraries from registries (PlatformIO, Arduino). Lookalike packages imitate trusted libraries (e.g. Arduin0Json, PubSubCllient) or introduce hidden network exfiltration in simple sensor drivers.

Who is Affected

Embedded developers using AI coding tools (Cursor, Copilot, Lovable) and the end-users who deploy the connected devices, smart meters, medical monitors, and industrial controllers they ship.

CORE METHODOLOGY

2. Four Analysis Dimensions

A multi-layered defense pipeline combining deterministic explainability with machine learning.

🔤

① Package-Name Similarity

Measures Levenshtein distance, Jaro-Winkler metrics, and lookalike character substitutions (0→o, 1→l, v→u) against canonical registries (ArduinoJson, PubSubClient, Adafruit_Sensor, ESPAsyncWebServer).

👤

② Publisher & Package Metadata

Verifies maintainer identity against verified namespaces (bblanchon, knolleary, adafruit). Flags repository origin mismatches, suspicious forks, and sudden unverified publisher releases.

🔍

③ Static Source Indicators

Detects hidden socket/WiFi calls, credential-related identifiers (WiFi.psk(), WiFi.SSID()), memory function pointer execution, PlatformIO compiler build hooks (extra_scripts), and hex/XOR obfuscation.

⚡

④ ESP32 Hardware Context

Validates declared hardware profile vs actual library behavior: flags ambient sensor libraries touching WiFi radios, direct NVS flash partition reads, and tampering with ESP32 bootstrap strapping pins (GPIO0, 2, 12, 15).

5. Failure Analysis & Safety Protocol

Rigorous documentation of static analysis limitations, edge cases, and safety controls.

FAILURE MODE 1

Malicious Packages with Unrelated Names

Attackers publishing novel utility libraries that strictly mimic legitimate networking patterns will bypass name similarity filters. ShipSafe counteracts this via hardware context checks, but if the declared purpose includes network permissions, subtle exfiltration may require runtime dynamic analysis.

Mitigation: Enforce strict egress domain whitelisting in firmware network stacks.
FAILURE MODE 2

Obfuscated or Dynamically Activated Behavior

Payloads triggered only after specific physical sensor thresholds (e.g. temperature > 50°C) or dynamic timing delays (sleep for 72 hours) remain dormant during compile-time static inspection.

Mitigation: Complement static gates with JTAG hardware-in-the-loop (HIL) automated test benches.
FAILURE MODE 3

Conditional Compilation & Missing Board Wiring

Complex #ifdef macros targeting specific chip silicon revisions or board wiring absent from the declared profile can mask pin conflicts or memory addresses.

Mitigation: Parse PlatformIO build environment matrices across all target build flags.
